**怎么发现的**,不复述代码逻辑。引擎选型与性能数据在

截断的下载被当成成功、录音静默丢帧、热键静默失效。

## 改源文件一律用编辑工具,不要用 shell 拼字符串

**动手前的判据:我是不是在用 shell 或内联脚本去改一个源文件?
是就停,改用编辑工具。** 不看这次的替换有多简单。

这条被踩了**五次**,每一次的自我辩解都是同一句:"这次只是个简单替换"。

| # | 怎么坏的 | 表现 |
|---|---|---|
| 1 | `bash -c` 套 `python -c "...中文..."` 传多行脚本 | 进程**卡死在 9MB working set、CPU 0%**,不报错也不退出;`Win32_Process` 里看到的 CommandLine 中文已经乱码 |
| 2 | `python - <<'PYEOF'` 做替换,内容里带 `\n` | `\n` 被当成真实换行写进目标文件,把字符串字面量从中间截断 → `SyntaxError: unterminated string literal` |
| 3 | 同上,f-string 里的 `\n` | 匹配串和文件内容对不上,`assert` 拦住了 —— 这次没写坏,纯属运气 |
| 4 | 正则删整行,**缩进不在匹配范围内** | 语句删了缩进留着,和下一行的缩进叠起来 → `IndentationError` |
| 5 | 正则 `.*?` 摘掉一段旧目录 | 非贪婪匹配越过了边界,**把紧随其后的一整条记录一起删了** —— 而被删掉的正是本条 |

第 1 条对应全局 CLAUDE.md 里"含特殊字符的命令一律走文件"那条。

**为什么写了还是会犯:**前几次的记录都是战报体("这次是这样坏的"),
不是动手前能查的判据。所以判据放在最前面,证据放在后面 ——
证据是用来说服自己"这不是偶然"的,判据才是拿来用的。

第 5 次尤其说明问题:当时正在做的事情就是**整理这条记录本身**,
而删掉它的手法正是它警告的那一种。**改 Markdown 也算改源文件。**

顺带一条独立的:内联脚本里 `print` 要加 `flush=True`(或设
`PYTHONUNBUFFERED=1`),否则进程被 C++ 层硬退出时缓冲区里的输出全丢,
排查时看到的是一片空白。

## 「恢复剪贴板」只对纯文本成立,别的都被静默销毁

`output.py` 顶部一直写着"用户复制在剪贴板里的东西不能被默默吞掉"。
实测下来,那句话只对纯文本成立:

| 剪贴板里原本是 | 说一句话之后 |
|---|---|
| **图片**(截图) | **没了** —— 备份的是 `.text()`,对图片是空串,还原等于 `setText("")` |
| **复制的文件** | 退化成一个 `file:///...` 字符串,粘不出文件 |
| **带格式的富文本** | 格式丢光 |
| 纯文本 | ✓ 完好 |

三种都是**静默的数据丢失**:用户复制了张截图,对着 AI 说一句话,图就没了。

**这个坑是"证伪轮"挖出来的** —— 挑一条从没验证过的假设,设计一个能让它
出错的场景去跑。读代码其实一眼就能看出 `.text()` 存不下图片,但一直没人去看,
因为它的测试全都只测纯文本 —— **测试覆盖的是它声称支持的场景**。

### 修的过程中又踩了三个

**1. "遍历 formats() 逐个 setData" 这个标准深拷贝写法,对图片静默失败。**
实测 `data("application/x-qt-image")` 返回 **0 字节** —— 图片在剪贴板里是个
QVariant 而不是原始字节。必须走 `imageData()` / `setImageData()`。

**2. `QClipboard.setMimeData()` 在 offscreen 平台上让 PySide6 退出时段错误。**
五行复现,和本项目无关;`setText()` 没事。`shiboken6.invalidate`、
保持引用都不管用。真实 windows 平台上不复现。
所以**不能长期持有那个 QMimeData** —— `setMimeData` 会接管所有权。
现在快照只存纯数据(`{格式: bytes}` + 一个 QImage),还原时现造一个交出去。

**3. 把"备份失败"和"本来就是空的"混成了同一个 `None`。**
剪贴板原本为空时应该还原成空,而返回 None 被当成"别还原",
于是识别结果留在剪贴板里不走了。单元测试当场抓到。

### 还有一条关于测试方式本身的

阻塞版 `paste()` 在**真实 Windows 上还原不了富内容**:sleep 期间事件循环是死的,
而 Windows 剪贴板要靠窗口消息才能完成交接。同样的内容走 `paste_async` 全部正常。
offscreen 平台的剪贴板是进程内的,不经过这套机制 —— **所以单元测试看不出这个差别**,
我一度以为是修复本身坏了。

### 代价:我在用户真实剪贴板上跑了破坏性实验

验证时我先检查了"当前不是图片/文件,所以安全",然后跑了一遍 —— 结果被测的
代码本身是坏的,把用户浏览器里复制的内容清空了。
**"检查过所以安全"的前提是被测代码正确,而那正是要验证的东西。**
这类实验要么在隔离环境里做,要么先用一个已知可靠的方式把内容存下来。

## Qt 的 offscreen 平台没有字体,截图会骗人

用 `QT_QPA_PLATFORM=offscreen` 渲染界面截图,中文全是豆腐块,看着像程序有
字体问题。实测两个平台的字体族数量:

| 平台 | 字体族数量 | `Microsoft YaHei UI` | `inFont('你')` |
|---|---|---|---|
| offscreen | **0** | 不存在 | False |
| windows | 333 | 存在 | True |

**offscreen 平台压根不加载系统字体**,跟程序本身无关。

渲染截图要用真实的 windows 平台,靠**不调 `show()`** 来避免弹窗——
`QWidget.grab()` 会自己把布局跑完并渲染到位图,不需要窗口可见。
见 `bench/render_ui.py`。

(offscreen 仍然适合跑 UI 单元测试,那里不关心字形。)

## windowed 打包后卡死是完全静默的

PyInstaller 用 `console=False` 打出来的 exe **没有 stdout**,一旦卡在 import 阶段:

- 命令行看不到任何输出
- 自检写的报告文件是**空的**(因为连 `run()` 第一行都没执行到)
- 进程列表里能看到它活着,但 CPU 几乎为零

两个必备手段:

1. **启动面包屑**:在 `__main__.py` 里、**导入任何重量级模块之前**就开始往文件里
   逐行写,每个 import 前写一行。只用 `os/sys/pathlib`,它们不会是卡住的原因。
2. **可切换的控制台版**:spec 里 `console=os.environ.get("VOICEINPUT_CONSOLE") == "1"`,
   调试时打一个能看到 traceback 的版本。

另外自检类脚本**必须每步落盘**,不能攒到最后一次性写——
卡住的时候正好就是写不到最后那一步的时候。第一版就是这么写的,白跑了一轮。

顺带一个打包时的小坑:`dist/` 删不掉报 `WinError 32`,通常是
**某个终端的当前目录还停在 `dist/VoiceInput` 里**(或程序还开着)。
光看 traceback 想不到这一层,`build.py` 里已经改成给人话提示。

## 录音有两条静默丢音频的路径

初版 `Recorder._callback` 有两处会让音频**悄无声息地少掉**:

1. **超过 `max_seconds` 后直接 `return`**。说满 120 秒还在继续说,松开只转前
   120 秒,没有任何提示。
2. **`status` 参数被整个忽略**。PortAudio 的 `input_overflow`(系统忙不过来、
   采集缓冲被覆盖)就在里面 —— 溢出意味着中间真的掉了音频,但转写结果看着
   是完整一句话,用户根本发现不了。

顺带一提,当时还有个 `_overflowed` 字段只在 `start()` 里置 False、
**从来没有被置 True 过**,是个纯粹的死字段。

修完之后单元测试立刻又抓到修复本身的 **off-by-one**:
判断写成"已录 ≥ 上限才拒绝",于是**单个超长块会被整块放行**;更糟的是,
如果用户正好在上限处松手、不再有下一个回调,`truncated` 就永远不会被置上。
正确写法是按**剩余容量**裁剪:

```python
remaining = self._max_frames - self._frames
if remaining <= 0:
    self._truncated = True
    return
if frames > remaining:
    self._truncated = True
    self._frames += remaining
    self._queue.put(indata[:remaining].copy())
    return
```

(不能在回调里关流:回调跑在 PortAudio 自己的线程上,在里面关流会死锁。
只能留下标志位交给上层。)

现在超限和溢出都会在悬浮条上给**黄色警告**(区别于红色错误:错误是"这次没成",
警告是"成了但不完整,你可能要补说一遍"),文字照常粘贴 —— 残缺的总比没有强。
录音时悬浮条右上角还会显示已录时长,超过上限 80% 时连上限一起显示,
把限制变成看得见的东西,而不是撞上去才知道。

## 分页内容超出窗口高度时 Qt 会把控件压扁

不是滚动、不是裁切,是**把每一行压扁去凑合** —— 下拉框的文字被挤成一半高。
触发条件比想象中容易:热键那栏多出两行冲突警告就够了,更别说小屏幕或
放大的系统字体。

解法是每个分页套一层 `QScrollArea`(`setWidgetResizable(True)`,
横向滚动条关掉)。有自己表格的分页(词典、历史)不用套 —— 表格本身会滚。

**顺带记一个差点误判**:加了滚动区之后截图里底部的下拉框看着还是压扁的,
差点又去"修"一遍。把窗口调高到内容完全放得下再截,一切正常 ——
那是 `grab()` 在滚动视口边界的裁切假象,不是 bug。
**截图看到的异常,先确认不是渲染方式本身造成的。**

## 热键配置错了是静默失效的

两个动作绑成同一个组合时,`_best_match()` 只能任选一个,另一个**永远不会触发**,
而且没有任何提示。原来的实现按字典序遍历,连"选哪个"都不确定。

两件事:

1. `_best_match()` 改成按 action 名排序遍历 —— 这种配置本身是错的,
   但运行期至少要**确定**,不能这次触发这个、下次触发那个。
2. 加 `validate()`,在设置界面当场标红。检查:写法不合法、没有修饰键
   (纯字母会把正常打字整个劫持掉)、两个绑了同一个组合、撞常用快捷键。

**子集关系不算冲突**:`<ctrl>+<cmd>` 是 `<ctrl>+<shift>+<cmd>` 的子集,
这正是默认配置,`_best_match` 取最具体的那个,是设计好的行为。

关于"撞常用快捷键"只能提醒、无法规避:pynput 用的是**底层键盘钩子,不吞按键**。
撞了不是"我们收不到",而是**两边同时触发** —— 你想说话,顺手把文件另存为了。

`validate()` 的返回结构也踩了一下:最初返回 `{action: 问题}`,于是"两个绑了
同一个组合"会被报成两条,界面上出现「甲和乙…」「乙和甲…」两行说同一件事。
改成返回 `list[Problem]`,`Problem.actions` 把涉及的动作放在一起,一个问题只报一次。

## 配置变更没防抖 = 拖一次数字框触发几十次模型重载

`configChanged` 原来在每次数值变动时立即发出。实测:

| 操作 | 触发次数 |
|---|---|
| 「粘贴前等待」从 80 拖到 200(步进 5) | **24 次** |
| 词典改一个单元格 | 1 次 |
| 单次 `config.save()` 耗时 | 0.44 ms |

**光看写盘会得出"没问题"的结论**——24 × 0.44ms ≈ 10ms,可以忽略。
差点就这么放过去了。

真正的问题是配置分发(当年是 `app._on_config_changed()`,现在是
`Settings.update()` + 各家的 `apply(cfg)`)不只写盘:它要通知一串子系统,
`engine.num_threads` 变了就调 `_reload_engine()`。而线程数就是「引擎」页的一个
数字框——**拖动时每变一步都触发一次完整模型重载(每次约 3 秒)**,
从 8 拖到 16 就是 8 次重载排队,二十多秒抖动。

解法:`MainWindow` 里加 300ms 单次定时器合并改动。两个配套的点:

- **热键冲突提示不走防抖**,立刻更新——那是本地反馈,延迟 300ms 才标红显得迟钝。
- **退出和关窗口时必须 `flush_pending()`**,否则用户改完最后一项就关掉,
  那次改动会随着没触发的定时器一起丢掉。

顺带被测试揪出一个小疏漏:问题修复后只 `setVisible(False)` 而没清空标签文字。
界面上看不见(隐藏了),但留着过期文案,将来可见性逻辑一改就会把早就修好的
问题又显示出来。

**这条的教训是:性能问题要看它触发了什么,不能只看它自己有多快。**

## 三个状态竞争,都表现为"卡住"或"状态不对"

这类问题正常使用中不常见,但一旦出现最难排查 —— 因为现象和原因隔得很远。

### 错误恢复定时器互相覆盖

`_fail()` 原来用 `QTimer.singleShot(4200, ...)` 恢复常态。**4.2 秒内失败两次
就有两个定时器在跑**:先到的那个把状态重置成"就绪",而第二次失败的错误还挂在
界面上;更糟的是这期间若已重新开始录音,过期定时器会在**录音中途**
把状态改成"就绪"。

两处都要改:用**同一个**定时器并重启(不是每次起一个新的),
且回调里确认 `recorder is None and not _busy` 才恢复。

### `_busy` 卡住 = 热键彻底静默失效

`_busy` 在识别开始时置 True、拿到结果时置 False。万一 worker 因为任何原因
不返回(模型崩了、线程卡死),`_busy` 会**永远**是 True,
之后按热键**什么都不会发生、也没有任何提示**。

加了 30 秒看门狗(正常识别 0.3 秒)。超时就放开 `_busy` 并报错 ——
"识别超时,已恢复可用"比"按了没反应"强太多。

### 向导关闭后回调仍会执行

标定录音发出去之后关掉向导,结果回来时回调指向向导里的控件,
而向导的 Qt 对象已经销毁 —— 抛 `RuntimeError`。
向导关闭时要显式丢弃 `_wizard_cb`。

## 截断的下载会被当成成功

真跑一遍模型下载(不 mock)才发现的一串问题。

### 先是一次误判

第一次真实下载 21 秒后失败:`WinError 10060`。当时的结论是
"GitHub release 在国内经常不通"。**这是从单次失败过度概括**——
用 curl 测三个源(github / huggingface / hf-mirror)都能下,500–600 KB/s;
第二次跑 Python 下载也完整通过,58.9 秒。

**真相是偶发网络抖动**。但由此暴露的问题是真的:155MB 的传输遇到一次抖动
就整个失败、从 0% 重来,报错还是原始的 `WinError 10060`。

### 然后是自己写出来的静默失败

加了重试和断点续传之后,用本地 HTTP 服务模拟"传到一半掐断"来测,
结果一测就炸 —— 而且炸在一个很典型的地方:

**连接被中途掐断时,`resp.read()` 可能干净地返回 EOF,while 循环正常结束,
于是 `_download()` 返回 True,截断的下载被当成成功**,一直到解压才报
`not a bzip2 file`。

修法是**核对字节数**,不能只看循环有没有正常退出:

```python
if known and got < total:
    raise IncompleteDownload(f"只收到 {got}/{total} 字节,连接被中断")
```

不能依赖异常类型来判断传输完整性 —— 网络中断不保证抛异常。

### 其它几条

- `.part` 文件要放**目标目录**而不是临时目录。放临时目录的话 `finally` 一删,
  错误提示里那句"已下载的部分会保留"就成了假话。
- 解压失败(包坏了)必须删掉 `.part`,否则续传会一直往坏文件后面追加,
  永远好不了。
- 续传时 `Content-Length` 是**剩余**长度,算进度要把已下载部分加回去,
  否则进度条会倒退。
- 服务器不支持 Range(回 200 而不是 206)时要从头重下,
  绝不能把新内容追加到旧文件后面。

## 历史「重新粘贴」会粘进程序自己的搜索框

功能自相矛盾的一个例子。

用户点主窗口里的「重新粘贴选中」时,**前台窗口就是 VoiceInput 自己** ——
直接发 Ctrl+V,文字粘进的是它自己的历史搜索框,而不是目标应用。

当时的提示文案写着"粘贴会发到当前的前台窗口,所以先切到目标窗口再操作"。
可切走了就点不到按钮了 —— **按文案描述的方式根本用不了**。

修法:点击后先把主窗口 `hide()`,延迟 300ms 让系统把焦点还给用户上一个窗口,
再发 Ctrl+V;同时用悬浮条给个反馈,因为窗口已经藏起来了,
不说一声用户不知道到底粘没粘。

**教训**:写提示文案的时候如果需要用户做一件"做了就没法继续操作"的事,
说明这个功能的设计本身有问题,不是文案不够清楚。

## "回到就绪"这件事在五个地方各写了一遍

上一条修的是**一个**过期回调覆盖状态的问题。回头一查,同样的逻辑
(`"就绪" if self._engine_ready else "模型未加载"`)在五处各写了一遍:
引擎加载完成、识别完成、错误提示过期、配置变更、暂停切换。
**其中只有一处有守卫** —— 也就是上一轮顺手修的那处。

于是"录音中被改成就绪"这个 bug 在另外四条路径上照样存在。
比如程序刚启动、模型加载完成的那一刻你正好按住热键在说话,
`_on_engine_loaded` 就会把"正在聆听"盖成"就绪"。

统一成两个方法:

- `_current_idle_state()` —— 空闲时该显示什么,**只此一处**
- `StatusPresenter.refresh()` —— 刷新状态,但**正在录音或识别时什么都不做**
  (当年叫 `app._refresh_state()`,后来连同这条守卫一起搬进了 StatusPresenter)

顺带修好了一个原先没注意到的 bug:暂停状态没有被这段逻辑考虑进去,
暂停期间若有错误提示过期,状态会显示成"就绪" —— 而此时按热键根本不会有反应。

另外 `_reload_engine()` 在录音中也不再改状态栏了。加载照常进行,
但把"正在聆听"盖成"正在加载模型…"会让用户以为录音断了。

**教训**:修复一个竞争条件时,先搜一遍同样的模式在别处有没有。
散落五处的重复逻辑意味着这个 bug 有五个实例,而不是一个。

## 「粘贴并发送」这个热键基本永远不会生效

**组合键按不可能同时按下。**

按 Ctrl+Shift+Win 时,按到 Ctrl+Win 那一刻 `_best_match()` 就已经命中
「粘贴文字」并触发了;之后再按下 Shift 时 `_active` 已被占用、不再重新判断。
于是行为完全取决于按键顺序,而最自然的顺序恰好是错的 ——
**「粘贴并发送」几乎永远不会生效**。

这个 bug 在代码里躺了很久,单元测试也有 25 条热键测试,
但它们只测了 `_best_match()`(给定按下的键集合,选哪个组合),
**没有一条测过完整的按下→触发→松开流程**。
补上按键状态机的测试,第一条断言就红了。

修法**不是加延迟消歧** —— 那会牺牲 push-to-talk 的即时感。
关键观察是:**两个动作录的音频完全一样**,区别只在结束时要不要补一个回车。
所以:

- 按下时照常立刻开始录音(零延迟)
- 同时记住本次按下期间命中过的**最具体**组合(`_peak`)
- **松开时按 `_peak` 决定动作**

顺带加了个 `on_upgrade` 回调:补按修饰键让动作升级时,把悬浮条文案改成
"正在聆听(说完直接发送)",否则界面说的和实际要做的不一致。

**教训**:测试覆盖了一个模块,不等于覆盖了它的**行为**。
`_best_match()` 是纯函数、好测,所以测得很细;而真正决定用户体验的
按下/松开时序是有状态的、难测,就被跳过了 —— 偏偏 bug 就在那里。

## 改错一个设置,整个程序就不能用了

`EngineWorker.load()` 的第一行原本是 `self._engine = None`,**然后**才去加载新的。
典型的"先释放后获取"。

于是模型目录敲错一个字母 → 重载 → 旧引擎已经被丢掉 → 新的加载失败 →
**什么都没了**。而用户可能只是想调一下线程数。

修法是把顺序倒过来:新的加载成功之前绝不动旧的,成功之后才 `unload()` 旧的。
代价是切换瞬间内存里有两份模型(约 500MB),但那是瞬时的,
比起弄丢一个能用的引擎划算得多。

### 修一半会被上层抵消

worker 改完之后旧引擎确实还活着,但热键仍然被拒 —— 因为 App 层有自己的
`_engine_ready` 标志:`_reload_engine()` 一上来就置 False,
`_on_engine_failed()` 又置 False。**worker 层修好了,应用层照样把它禁掉。**

所以 `loadFailed` 信号加了第二个参数"是否仍有可用引擎",让 App 据此决定:

- 旧引擎还在 → 保持可用,悬浮条给**黄色警告**"新模型没加载成功,仍在用之前的模型"
- 首次加载就失败 → 才是真的红色错误

同时 `_reload_engine()` 不再提前把 `_engine_ready` 置 False ——
重载期间旧引擎可用,提前禁掉只会让"改个线程数"这几秒里按热键直接没反应。

**教训**:一个状态在两层各存一份时,只修一层等于没修。

设置页和向导都要"选麦克风 + 看电平",两边各写了一份,各约 40 行。

破折号不同、措辞不同。改了一处,另一处继续过时。

向导进到那步自动测),但**监听本身、电平换算、结论文案只有一份**。

旧的 `LevelMonitor` 还连在上一个设备上。组件里统一处理了。

**判断要不要抽取的标准不是"重复了多少行",是"这段逻辑将来会不会改"。**
会改的重复才危险,因为它一定会漂移。

## 把配置字段逐条过一遍界面(方法本身值得记)

上一条总结出的找法,这次系统跑了一遍 —— 写个脚本比对
`Config` 的每个字段和界面代码里的 `cfg.xxx`,列出"界面上改不了的"。
24 个字段里揪出 5 个,分成三类:

### 真缺口:`output.send_delay_ms`

Ctrl+V 到回车之间的等待。和已经暴露的 `paste_delay_ms` 是同一类问题,
**后果更严重**:目标应用慢一点,回车就赶在文字落地之前触发,
**提交出去的是空的或残缺的**。而"对着 Claude Code 连续说话"正是主场景。

### 陷阱:`audio.sample_rate`,直接删掉

实测(声明不同采样率喂同一段音频):

| 声明的采样率 | 识别结果 |
|---|---|
| 16000(真实值) | 开饭时间早上9点至下午5点。 |
| 8000 | 开饭时间早上9点至下午5点。 |
| 44100 | **下**饭时间早上9点至下午5点。 |

sherpa-onnx 内部会重采样,所以**不报错** —— 只是识别悄悄变差。
一个"改了不报错、只是结果慢慢变烂"的旋钮,摆出来纯粹是害人。
删掉字段,改用 `audio.SAMPLE_RATE` 常量。

### 本来就该藏的:`engine.name` / `engine.language`

前者只有一种实现,后者实测 `auto` 与 `zh` 输出逐字相同 —— 摆出来是个假旋钮。
两个都在 config.py 里写了为什么不暴露。

**不是所有配置项都该有界面。判断标准是"改了会发生什么":
改了有用的要暴露,改了没用的别摆出来,改了会静默变坏的直接删。**

## 最强调的那个坑,产品里没有防线

## 设备编号会漂,存编号等于埋雷

配置里 `audio.device` 存的是 PortAudio 的设备编号。**那是枚举序号,不是身份。**
插拔任何一个音频设备 —— 插个 USB 耳机、开关一个虚拟声卡 —— 编号就会重排。

后果:你精心选好的 29 号,某天变成了别的设备。录音悄悄录到那个设备上,
表现是"按了热键没反应"或"只录到静音"。**用户绝不会想到是编号漂了**,
只会怀疑程序坏了。

而这台机器上还叠加了另一层:系统里全是 RØDE Connect 的虚拟设备,
漂到隔壁很可能就是系统声音回环 —— 有电平、能录、就是不是你的声音。

实测确认 PortAudio 给的信息里只有 `name` + `hostapi` 是内容标识,
`index` 纯粹是序号。所以:

- 配置里同时存 `device_name` 和 `device_hostapi`,编号只当缓存
- 启动时**按名字解析**成当前编号
- 名字在但 hostapi 变了 → 用它,但提示一声
- 名字找不到 → **明确告诉用户"找不到之前选的麦克风,已回退到系统默认,请重新选择"**,
  绝不默默用系统默认

同一个设备在多个 hostapi 下名字**完全相同**,所以 hostapi 必须一起存,
只认名字会挑错那一个。

这条同时让 README 里"整个目录拷走即可在别的机器上跑"真正成立 ——
换机器时编号必然对不上,名字还有机会。

## 一直在拿"推理耗时"当"用户感受到的延迟"

引擎选型的全部论据是"SenseVoice 推理快 116 倍"。数字没错,
但**用户感受到的从来不是推理耗时** —— 是"松开热键到文字出现"这一整段。

十几轮下来,这个数字一次都没量过。所有文档写的都是 0.29s(推理),
而后处理、剪贴板、粘贴前等待全没算。

实测(`bench/latency.py`)端到端 **380ms**,推理占 79%。

结论是好的 —— 选型依据成立,后处理和剪贴板加起来不到 1ms,没有藏着的开销。
但**"0.29s"这个说法低估了 30%**,已经改成如实的 380ms。
换算到端到端,和 faster-whisper 的差距是 99 倍而不是 116 倍。

**教训:一个论据用了很多轮,不代表它量的是你以为的那个东西。**
"推理快"和"用起来跟手"之间隔着好几步,而那几步从来没被验证过 ——
只是碰巧都很便宜。

顺带发现一个可优化点:380ms 里有 80ms 是 `output.paste_delay_ms`,
纯粹是我们自己配的等待。粘贴稳的应用把它调小就能更跟手 ——
这是唯一一项用户能自己优化的。

## 给用户准备的脚本,自己从来没跑通过

`bench/` 里那套引擎标定链路(`record_samples` → `run_sensevoice` → `report`)
写好之后**一次都没端到端跑过** —— 因为它需要真人录音。
等用户真去录的时候才发现脚本坏了,是最糟的时机。

用 TTS 音频伪造一份 manifest 空跑一遍(只验证工具,不当标定结果),
链路是通的,**但暴露出一个方法论上的硬伤**。

### CER 会把正确的 ITN 输出判成大面积错误

朗读稿写「把超时改成**三十秒**」,开了 ITN 的模型输出「改成 **30** 秒」——
**内容一个字都没错**,逐字比却算出 **30.4% CER**。

后果很严重:真人标定时凡是含数字的句子都会被压出虚高的错误率,
SenseVoice 会显得比实际差得多 —— **足以导致选错引擎**。
而这个偏差在换真人录音之前完全看不出来。

修法是在 `norm` 口径里把中文数字和阿拉伯数字统一之后再比。
关键性质:**两边用同一套转换,所以转得不完美也只是"没修好真错误",
不会凭空造出假错误**。那条句子的 CER 从 30.4% 降到 8.3%。

顺带把朗读稿里「采样率用十六千赫兹」这种没人这么说的表述换掉了 ——
既难念,又是剩下那 8.3% 的来源。

**教训:为别人准备的东西,自己先走一遍。**
"语法没错"和"能用"之间隔着很远,而这次隔着的是一个足以让结论反转的偏差。

## 一半的麦克风选项是坏的(WASAPI 采样率)

实跑 `probe_devices.py` —— 这是用户要执行的**第一个**脚本,而它一次都没被
运行过 —— 结果三个 WASAPI 设备全部:

```
Error opening InputStream: Invalid sample rate [PaErrorCode -9997]
```

**WASAPI 共享模式只接受设备的原生采样率**,请求别的直接开不了流。
本机 WASAPI 设备原生是 48000,而 `Recorder` / `LevelMonitor` 都写死用 16000。

也就是说:**在设置里选中任何一个 WASAPI 设备,录音直接打不开** ——
而设备下拉框里一半的选项是 WASAPI,我还一直在文档里把 WASAPI 称作
"Windows 上最直接"的选择。

实测确认(修复前):MME 四个设备全通,WASAPI 三个全废,14 项里 6 项是坏的。

### 修法

按设备原生速率开流,把**真实**速率交给引擎:

- `native_sample_rate(device)` 查 `default_samplerate`
- `Recorder(sample_rate=None)` 表示"跟设备走"
- `Recorder.sample_rate` 把实际用的速率报出来
- 上层用 `recorder.sample_rate` 而不是常量去调 `transcribe`

实测 sherpa-onnx 对 16k / 44.1k / 48k 输入**如实声明**时结果逐字相同 ——
它自己会重采样。但**谎报**速率会让识别悄悄变差(见 config.py 那条),
所以"把实际速率传上去"这一步不能省。

修完 14 项全通。

### 三条连带的教训

1. **`SAMPLE_RATE` 这个常量骗了我两次。** 一次是把它当配置项暴露出去
   (谎报会静默降质),一次是把它当成"所有设备都能用的速率"。
   同一个数字在不同位置含义不同 —— 模型要求 16k,不代表采集端也能给 16k。
2. **旧测试依赖了本机声卡。** 它们构造 `Recorder(max_seconds=...)` 不给速率,
   改成"跟设备走"之后就跟着本机的 44100 跑了,帧数对不上。
   已改成显式指定 —— **测试不该依赖硬件**。
3. 又一次印证:**为别人准备的第一步,自己一定要先走。**

## 自检自己也漏了最关键的一环

上一条的 WASAPI bug 有个更值得追问的地方:**为什么它能混过十九轮打包验证?**

因为自检里那一项写的是:

```python
devices = list_devices()
say(f"[通过] 枚举到 {len(devices)} 个输入设备")
```

**只证明"看得见设备",没证明"打得开"。** 而一半的设备根本打不开。
每一轮我都跑了自检、每一轮都显示"全部通过"。

### 防线要反向验证过才算数

补上逐个试开之后,**把采样率临时改回写死 16000**,自检立刻报:

```
[失败] 3/7 个设备打不开 —— 设备下拉框里会有选了就用不了的选项
自检结果: 存在失败项
```

改回来再跑,全过。**这一步不能省** —— 不验证一遍,新加的检查很可能
只是又一个"看得见"级别的摆设,而你会更加放心。

### 顺着这个标准把自检重新过了一遍

问每一项:它验的是"看得见"还是"能用"?于是发现两个从来没被检查过的环节:

- **剪贴板** —— 每次听写的最后一步。前面全过、这里坏了,
  表现是"识别完了但什么都没粘出来"。
- **全局热键钩子** —— **整个程序的开关**。打包之后 pynput 装不上钩子的话,
  按热键什么都不会发生,而模型、界面、音频全都会显示"通过"。

两项都补了,并且在打包产物上验证通过 —— frozen 环境才是它们真正可能出问题的地方。
(热键那项启动即停,pynput 的监听器不吞按键,不影响正在用电脑的人。)

**教训:检查项的措辞就暴露了它的强度。**
"枚举到 N 个设备"和"N 个设备都能打开"听起来差不多,
差别是十九轮没发现一个致命 bug。

## 打包会静默删掉用户的配置和历史

**这一条是真的发生了,不是假想。** 2026-08-26 重新打包时,
`build.py` 的 `clean_dist()` 里那句 `shutil.rmtree(dist)` 把用户的
`config.toml` 和 `history.db` 一起删了。没有提示、没有备份、不可恢复。

根因是**绿色软件的数据位置和打包产物的位置是同一个目录** ——
这是绿色软件的正确设计(数据跟着 exe 走,整个目录拷走就能换机器),
但它让"清理旧产物"和"删除用户数据"变成了同一个动作。

在那之前的做法是"打包前记得手工备份"。**靠记性的步骤等于没有这个步骤**,
于是有一次就没记住。改成 `rescue_user_data()` / `restore_user_data()`
由打包流程自己做,并且:

- 备份放在 `dist` **之外**(放里面的话下一步 rmtree 会连备份一起删)
- 打包失败时不还原,但**必须打印备份在哪** —— 那时旧产物已经删了,
  备份是用户数据仅存的一份
- 新产物里已存在同名文件时不覆盖,并且说出来。静默二选一在这里
  无论选哪边都有人丢东西

验证方式是**真的往产物里写标记文件再完整重打一次**,不是读代码确认。

## 随机变红的测试比没有测试更坏

`tests/test_worker_dispatch.py` 的 `wait_for(signal)` 原来是:先 `emit`,
再连上信号进事件循环等。worker 跑在真的另一个线程上、FakeEngine 又是
瞬间返回的 —— 它完全可能**在主线程连上信号之前就已经发完了**,
于是等到 5 秒超时,测试随机变红。

它教人的东西是"再跑一遍就好了"。而这个项目里最贵的那个 bug
(`Q_ARG(object, …)` 导致模型从来没加载过)正是靠这组测试才钉住的 ——
一旦养成重跑的习惯,下一次真的坏了也会被当成抖动。

改成 `watch(signal)` 先架收集器、再触发。顺带副作用:这组测试
从 5.5 秒降到 0.4 秒 —— 之前那 5 秒全花在等一个永远不会来的信号上。

**判据:任何"等某个异步结果"的测试,收集器都必须在触发之前就位。**

界面上曾经写着这些:

- 「这台机器所有输入设备都是 RØDE Connect 的虚拟设备」
- 「本机实测:CPU 8 线程 RTF 0.054(18.4 倍实时)」

三句话都是真的 —— **在开发机上**。换台机器全是错的,而且错得很有欺骗性:
用户会以为程序认出了他的硬件,于是相信这个结论。

判据很简单:**用户看得见的文字里,凡是断言"这台机器怎样"的,
都必须来自运行时探测。** 代码注释里记录开发机的实测数字是好事

改法都是把断言换成探测:

- 设备提示 → `audio.suspicious_devices()` 按真实枚举到的设备名生成,
  并且**只用来多提醒一句,不用来禁用任何选项**(名字是厂商起的,
  列表永远列不全,唯一可靠的判据仍然是看电平)
- 性能数字 → `EnginePage.set_measured()`,显示这台机器刚跑出来的那一次
- 计算设备 → `asr/providers.py` 按发行包里带没带 CUDA 的 provider 库来判断

## 选了 CUDA 却在用 CPU,而且完全没有提示

sherpa-onnx 分 CPU 版和 GPU 版。CPU 版拿到 `provider="cuda"` **不报错**,
只往 stderr 打一行:

```
Please compile with -DSHERPA_ONNX_ENABLE_GPU=ON.
Available providers: CPUExecutionProvider, . Fallback to cpu!
```

然后照常用 CPU 跑完。而 windowed 打包之后根本没有 stderr ——
界面写着 CUDA、配置存着 cuda、实际跑在 CPU 上,没有任何地方会告诉用户。

`asr/providers.py` 现在按**发行包里带没带 `onnxruntime_providers_cuda.dll`**
来判断,不可用时:下拉框里根本不列出这个选项、引擎自己把 provider 落到 cpu、
模型加载完成时把落差说出来、自检里报失败。

## 纯修饰键的热键会被它的每个超集触发

默认热键曾经是 `<ctrl>+<cmd>`。它命中的条件是"Ctrl 和 Win 都按着" ——
于是 **Ctrl+Win+任何键都会触发它**:Windows 自己的虚拟桌面切换
(Ctrl+Win+左/右)、别的软件的 Ctrl+Win+X 热键,统统算。

用户报的"热键和微信冲突了"就是这个。**这不是微信的问题**,
是这个组合的结构性缺陷,从配置本身就能推出来,不需要知道装了什么软件。

更糟的是当时有一条测试叫 `test_modifier_only_combo_ok`,断言
`validate({"甲": "<ctrl>+<cmd>"}) == []` —— **把缺陷当成正确行为钉住了**。
现在它叫 `test_modifier_only_combo_is_reported`,断言是反的。

### 顺带:凭印象推荐"应该没人用"的组合,同样是错的

修这个问题时我推荐用户换成 `Ctrl+Alt+空格`。随后写了探测代码一跑 ——
**那个组合在他机器上已经被占用了**。哪个组合空闲取决于用户装了什么,
开发机上看不见。

`conflict.py` 用 Windows 的 `RegisterHotKey` 当场问系统:
某个程序注册了这个组合,别人再注册会拿到 `ERROR_HOTKEY_ALREADY_REGISTERED`。
实测在开发机上直接认出了微信的 `Ctrl+Alt+W` 和 `Alt+A`。

盲区要说清楚,不能让人以为探测通过就等于安全:

- 只看得见用 `RegisterHotKey` 注册的热键。走底层键盘钩子的程序
  (我们自己就是)不占用任何东西,撞了探测不出来
- 纯修饰键组合 `RegisterHotKey` 根本表达不了,返回"不知道"而**不是**"没被占"
- 探测时注册成功**必须立刻注销**,否则我们自己就成了占用者

候选表里的每一项必须**同时**能被 RegisterHotKey 表达、且能被 pynput 解析。
这条是测试抓出来的:候选里写着 `<ctrl>+<alt>+f9`,前者认、后者不认
(功能键要写 `<f9>`)—— 真被选中的话,用户点完「自动换一个」之后热键才失败。

## 自检的输出因为编码问题凭空消失

打包版自检里,两条热键结论从控制台不见了 —— 报告文件(UTF-8)里有,
控制台里没有。看起来像"那段代码根本没跑"。

真因:中文 Windows 的控制台是 GBK,而当时结论文案里带着 `✓` / `✗`。
**`✓`(U+2713)GBK 编不出来**,`print` 抛 UnicodeEncodeError,
被 `except Exception: pass` 吞掉,整行消失。

```python
>>> "✓".encode("gbk")
UnicodeEncodeError: 'gbk' codec can't encode character '✓'
```

**自检本身出现静默失败,比它要检查的那些问题更坏** —— 它正是用来
排除静默失败的那个工具。修法是 `selftest.report.safe_print()`:编不出来就用
`errors="replace"` 退化重打,字符可以变成问号,**但这一行必须留下**。

顺带一条判据:界面上用 ✓/✗ 没问题(Qt 直接渲染 Unicode),
**往控制台打的字符串要过一遍 GBK**。所以结论文案里不带记号,
记号由调用方拼 —— 界面拼 `✓`,自检拼 `[通过]`。

## 异常掩盖:清理代码抛的错盖掉了真正的错

同一次自检还报了 `[失败] 界面渲染: [WinError 32] 另一个程序正在使用此文件`。

真错是 `AttributeError: 'Wizard' object has no attribute '_stop_level'`
(重构时删掉了那个方法,而自检是唯一调用它的地方)。但 `history.close()`
写在顺序流末尾,异常一抛就跳过了它,sqlite 句柄还开着就走到
`TemporaryDirectory` 的清理 —— 于是抛出**文件被占用**,把真正的错误顶掉了。

修法是把 `close()` 放进 `finally`。**判据:任何持有句柄的清理都必须在
finally 里,否则它会在出错时变成一个假的错误信息。**

这一条也说明打包自检是不可省的:那个 `AttributeError` 单元测试一个都没抓到,
因为没有任何单元测试走"自检构造向导"这条路。

## 异步回调活得比它指向的控件久

向导的标定录音走的是异步转写:录完 → 派给 worker 线程 → 结果回来时调回调。
那个回调指向向导里的控件。用户如果在识别返回之前关掉向导,
回调就会对着已销毁的 Qt 对象写,抛 `RuntimeError: Internal C++ object
already deleted`。

**难查的地方在于时间差**:崩溃发生在识别线程回来的那一刻,离用户关掉
向导已经过去好几秒,现场早就没了;而且它抛在 Qt 的信号处理里,
是一次无人接管的异常。

`WizardHost` 现在守着这条不变量:向导一销毁就把等待中的回调丢掉。
另外 `deliver()` 里只吞 `RuntimeError`(控件没了),**不吞别的异常** ——
把 ValueError 之类一并吞掉就等于自己制造静默失败。

顺带一条 Qt 细节:`QTimer.start(ms)` 会**连间隔一起改掉**。
把"停留多久"写在每个调用点上,它就变成了调用点的事,而它其实是
那个对象的属性。间隔在 `__init__` 里 `setInterval()` 一次,
之后一律 `start()` 不带参数。

## 导入时算好的默认路径,让测试写进了真实数据库

`history.py` 里原来是:

```python
DB_PATH = app_dir() / "history.db"        # 模块级常量,import 时就定死
...
self._path = path or DB_PATH
```

后果是**测试没法把它重定向到临时目录**:`monkeypatch.setattr(history, "app_dir", ...)`
在 import 之后才执行,拦不住一个已经算完的常量。于是任何忘了传 `path` 的
测试都会往程序目录旁边那个**真实的历史库**里写。

实测就这么污染过一次:新写的 `HistoryHost` 测试往项目根目录的 `history.db`
里塞了两条"第 3 条""第 4 条"。而且它**测试全绿** —— 因为断言的是行为,
不是位置。

改成 `default_path()` 函数,求值推迟到构造那一刻。

**判据:任何"默认落在哪"的路径都要是函数,不能是模块级常量。**
常量版本在生产环境完全正确,只在测试里出问题 —— 而这类问题不会让测试变红,
只会悄悄改动你的真实数据。

## 滚一下设置页,路过的控件全被改掉了

设置页外面套着 `QScrollArea`,而 **Qt 默认把滚轮事件交给鼠标底下的那个控件**。
于是用鼠标滚设置页的时候,指针扫过哪个控件就改哪个:

| 滚过 | 结果 |
|---|---|
| 「触发方式」 | 从"按住说话"变成"按一下切换" —— 整个交互模式换了 |
| 「麦克风」 | 换成另一个设备,很可能是个回环 |
| 「线程数」 | 变了,并顺带触发一次三秒的模型重载 |
| 「单次上限」 | 录音上限被改 |

全程**不报任何错、界面也不跳回去**,滚过去就什么都不知道了 ——
正是这个项目一直在排除的那类失败。

发现方式是给设置窗口里每个控件发一个滚轮事件,前后比值:

```
[常规] 数字框  80  --滚轮--> 79    !! 被改掉
[常规] 下拉框  0   --滚轮--> 1     !! 被改掉
[引擎] 数字框  8   --滚轮--> 7     !! 被改掉
```

11 个控件里 10 个中招。

修法是 `WheelGuard`:没焦点就不接滚轮。**但这里有个坑中坑** ——
第一版写的是 `event.ignore()`,指望 Qt 自己把事件往上传给滚动区域。
实测传不上去:鼠标停在数字框上时整个页面滚不动了,修一个坏一个。
所以改成自己沿 parent 链找到 `QAbstractScrollArea`,把事件明确 `sendEvent`
过去。

**判据:凡是"靠框架默认行为兜底"的地方,都要有一个测试把那个默认行为钉住。**
`ignore()` 到底会不会往上传,取决于 Qt 版本和事件是怎么投递进来的 ——
那不是能凭记忆下结论的事。

## 数字框默认步长 1,用户说"这个是不能用的"

用户报的原话是「设置里面的上下调整数值的,这个是不能用的」。
先怀疑是样式表把上下箭头搞坏了(样式表接管 QSpinBox 之后箭头消失是常见问题),
于是分三步验:

1. 数样式表下箭头区域的像素 —— **画出来了**,不是消失。
2. 用 `QStyle.subControlRect` 取到按钮矩形,`QTest.mouseClick` 点中心 ——
   **值确实变了**,不是点不动。
3. 看变成了多少 —— `2000 -> 2001`。

问题在这里:所有数字框都用了 QSpinBox 的默认步长 1,而框里放的是
80 毫秒、1200 毫秒、2000 条。点一下箭头数字纹丝不动,**看起来就是坏的**。

顺带记一条探针自己的错:第一版探针把上箭头当成在控件的上半部分,
点 `(w-10, h//4)`,结果两次都是减。**Windows 11 的 spinbox 箭头是左右排布,
不是上下** —— 差点据此断言"上箭头失效"。位置要问 `subControlRect`,不能自己按
宽高算。

**判据:数字框的步长要按框里那个数的量级给,不能按范围给。**
历史条数范围是 50~100000,上限只是个不想设限的大数;按范围的百分之一算
会要求步长一千,那是另一个方向的难用。用户看着的是框里那个数。

## 界面文案里的 markdown 星号原样显示了出来

音频页的设备说明在界面上长这样:

```
注意:「System Input (RØDE Connect)」这类名字通常是**系统声音回环**而不是话筒
**别按设备名猜** —— 名字好听的未必是话筒
```

写这些文案的时候是照着文档的语气敲的,`**` 顺手就打上去了,而 `QLabel`
默认按纯文本显示。**这类错误代码审查看不出来** —— 源码里那两个星号看着完全正常,
只有把界面真的画出来才看得见。

修法不是把星号删掉(下次写文案的人还会再写),而是让 `hint()` 把
`**x**` 转成 `<b>x</b>`。注意顺序:**先 `html.escape` 再替换**,
否则文案里的 `<ctrl>` 会被当成标签整段吞掉。

**判据:界面改动要看渲染结果,不能只看源码。**
这一轮三条问题(滚轮、步长、星号)全是靠"把窗口真的画出来 / 真的发事件"
发现的,读代码一条都发现不了。

## 标定的判据里混进了被测对象本身

向导第三步要回答一个问题:**这个设备是不是我的话筒。**
判据是念一句话、算字错误率。而那句话原来是:

```
把这个 function 改成 async
```

选它的理由是"贴近真实使用场景"。这个理由害了它:**SenseVoice 对口说的
英文术语本来就不准**,`async` 会被听成别的词。于是字错误率轻松越过 20%
的红线,程序回答:

> ✗ 和原句差得比较多(字错误率 33%)。可能是设备选错、离麦克风太远,或者环境太吵

**话筒完全正常的人,被告知设备可能选错了。** 而这一步存在的全部意义,
就是把"设备选错"这个假象排除掉 —— 它自己成了假象的来源。

改成纯中文句子。英文术语准不准是「词典」页要解决的事,和"设备对不对"
是两件事;混进同一个判据里,结果是两件事都判不准。

**判据:一个用来诊断 A 的测试,里面不能含有会因 B 而失败的成分。**
否则你分不清报警是 A 坏了还是 B 坏了 —— 而分不清的报警比不报警更坏,
因为它会指使人去改一个没坏的东西(这里是去换一个好好的话筒)。

已经用一个测试把它钉住了:标定句里出现任何 ASCII 字母就变红。
理由写在测试的 docstring 里,免得将来又有人觉得"加点英文更贴近真实场景"。

## 桌面上的按钮右键没有菜单

悬浮麦克风是个常驻桌面的圆按钮。**出了问题,人的第一反应是右键点它。**
以前右键什么都不发生,唯一的出路是去系统托盘里找那个 16 像素的图标 ——
而托盘图标很可能正被 Windows 折叠在"显示隐藏的图标"里面。

这类问题不会出现在任何测试里,也不会出现在需求清单里:功能"都实现了",
只是**没实现在人会去找的地方**。

修的时候有两件具体的事:

**1. 菜单要用托盘那一份,不能另建。** 两份菜单会漂移成不一样的选项,
而且是没人会发现的漂移 —— 很少有人同时右键托盘和右键悬浮麦克风。
(这条在本文档里已经是第二次出现了,见「重复的代码不会静静躺着」。)

**2. 必须用 `exec()` 而不是 `popup()`。** 悬浮麦克风是
`WindowDoesNotAcceptFocus` 的。实测:

| 方式 | 250ms 后 | 700ms 后 |
|---|---|---|
| `exec()` | 可见 | 可见 |
| `popup()` | **已经不见了** | — |

`popup()` 之后函数立刻返回,菜单当场失去激活自己关掉,表现是
"右键闪一下什么都没有"。这个差别读文档看不出来,是跑出来的。
